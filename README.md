# Benchjot

**A research jotter for your code.**

Live: https://benchjot.vercel.app · Android app: [Ozovehe1/benchjot-android](https://github.com/Ozovehe1/benchjot-android)

Benchjot is a notebook for experiments. Each note holds what you meant to try, the code you ran, what it printed and drew, and whether it worked. Notes link to each other, so a line of work (attempt 1, attempt 2, the fix that finally worked) stays visible as a map instead of getting lost in scattered scripts and chat logs.

## The problem

Students and researchers who write code run many small experiments: change a parameter, rerun, try another model, fix an error, try again. The code usually ends up in one place (a script, a notebook, a phone), the reasoning in another (a paper notebook, a chat, memory), and the outcome nowhere. A week later it is hard to say which attempt worked, what was changed between attempts, or why one was abandoned. Benchjot keeps the intent, the code, the output and the outcome together in one note, and keeps the relation between attempts.

## What it does

- **Notes with code cells.** A note has a title, a Markdown body (with LaTeX math via KaTeX) and any number of code cells, typed or uploaded. Cells are edited in CodeMirror 6 with highlighting for Python, JavaScript, TypeScript, C, C++/CUDA, Go, Rust, Java, MATLAB, R, Julia, Shell, SQL, JSON, YAML and Markdown (`src/lib/languages.ts`). New cells default to Python.
- **Runnable cells in the browser.** Python runs in Pyodide in a Web Worker (`public/workers/python.js`, Pyodide 0.29.3; imported packages are loaded on demand, others via micropip). JavaScript and TypeScript run in a worker (`public/workers/js.js`, TypeScript transpiled with sucrase). Python cells have Ruff lint and **Autofix** (`@astral-sh/ruff-wasm-web`).
- **Cell notes.** Each code cell has an optional "Note before run" (what you expect) and "Note after run" (what happened), written only by you.
- **Saved runs and figures.** Each cell keeps its latest run (stdout/stderr, error, time) and shows it on reopen, marked "Output from an earlier version" once the code changes. One capture module (`public/workers/bj_capture.py`) collects matplotlib / seaborn / pandas plots, sklearn displays, PIL images, pandas tables (preview + CSV) and Plotly, Altair (Vega-Lite) and Bokeh charts. Each output opens on its own page and downloads as PNG, JPG, WebP, SVG, PDF, CSV or JSON as the output allows, or the whole run as a zip. Files live in a private Supabase Storage bucket (`run-outputs`).
- **Outcome.** A note can be marked Successful or Failed (or left unmarked). Only you set it; runs, errors and the AI never change it. The note list filters by outcome together with search and project.
- **Projects, sub-notes, links, attempts.** Notes can be filed in projects (folders), nested under a parent note, linked with `[[Title|id]]` (typing `[[` offers titles; Linked from shows backlinks), and started as a **New attempt** of another note (`entries.derived_from`).
- **Research Map** (`/map`). A graph of your notes (d3-force): links solid, sub-notes dashed, attempts as bold arrows; marks show the outcome (hollow = unmarked, filled = successful, diamond = failed). Two lenses: Around a note (depth 1–3) and Everything, plus a "Map as list" view.
- **Fix.** After a run fails, Fix sends the code and the error tail to the server, which asks Groq's `openai/gpt-oss-120b` for a corrected file. It is shown as a minimal diff you accept or reject.
- **Helper** (top bar → Helper, "Online helper"). *Write code* or *Ask this note*, with suggestion chips "Run this experiment", "Plot the results", "Explain this code". The note is read only when you send: body, then each cell's notes, code, and last output or error. Proposed code is added only when you tap **Insert into note** (as a new cell); it never runs by itself and never writes note text, cell notes or the outcome. Turns are saved per note (`helper_turns`) for 30 days, then condensed by the database into one summary per note (`helper_summaries`).
- **Run on server (Pro).** `POST /api/run` runs Python, C, C++, Go, Rust or Java in a Modal Sandbox. Options are comments in the cell: `# pip: torch transformers`, `# gpu: T4` (Python only; T4, L4, A10G, A100), `# timeout: 120` (5–240 s). Pro is the `profiles.plan` column, which users can read but not write; there are no payments.
- **Read-only example note** on the signed-out landing page: a real digits experiment (logistic regression vs random forest) with its real run output, generated by `scripts/sample-note/make.py`.
- Sign-in with email or username and password, or Google. Installable as a PWA (`public/sw.js`, offline shell).

## Run it locally

Requires Node.js 20+ and a Supabase project.

```bash
cp .env.example .env.local   # set NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY
npm ci
npm run dev                  # http://localhost:3000
npm run check                # typecheck + lint + unit tests (vitest)
npm run build                # production build
```

Environment variables (names only; never commit values):

| Variable | Needed for |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Everything (public; data is protected by Row Level Security) |
| `NEXT_PUBLIC_GOOGLE_CLIENT_ID` | Google sign-in (optional; `src/lib/env.ts` has a default) |
| `GROQ_API_KEY`, optional `GROQ_MODEL` (default `openai/gpt-oss-120b`) | Fix and Helper (server only) |
| `MODAL_TOKEN_ID`, `MODAL_TOKEN_SECRET` | Run on server (server only) |
| `SUPABASE_PROJECT_REF`, `SUPABASE_ACCESS_TOKEN` | `npm run db:migrate` only |

Database: apply `supabase/migrations/*.sql` with

```bash
SUPABASE_PROJECT_REF=<ref> SUPABASE_ACCESS_TOKEN=<token> npm run db:migrate
```

End-to-end checks against a deployment are in `scripts/` (Playwright; see `scripts/README.md`): `e2e_smoke.py`, `e2e_outcome.py`, `e2e_links.py`, `e2e_last_run.py`, `e2e_outputs.py`, `e2e_server.py`, and `rls_check.py` (a second account can't read or change the first account's rows or raise its own plan).

## Architecture

- **Next.js 15 (App Router), React 19, TypeScript, Tailwind CSS v4**, deployed on **Vercel**. Pushes to `main` deploy. GitHub Actions (`.github/workflows/ci.yml`) runs typecheck, lint, unit tests and build, and checks that the capture fixtures and the landing example note are current.
- **Supabase**: Postgres (tables `projects`, `entries`, `snippets`, `profiles`, `helper_turns`, `helper_summaries`, …), Auth, Storage (`run-outputs`). Every table is owner-only via Row Level Security. Migrations in `supabase/migrations/`. Helper history is condensed by `helper_condense()`, run hourly by pg_cron.
- **Code runs in the browser** for Python (Pyodide from jsDelivr) and JS/TS. The server never runs a free user's code.
- **Server routes** (`src/app/api/`): `run` (Modal Sandboxes; `src/lib/server/modal.ts`, Python image `python:3.12-slim` with numpy, pandas, scipy, matplotlib, seaborn, scikit-learn, pillow, plotly, altair, bokeh preinstalled), `fix` and `helper` (Groq; one module `src/lib/server/groq.ts`, `temperature 0`, `reasoning_effort: "low"`, JSON replies). The Android app calls these routes with the user's Supabase access token.
- **Limits** live in `src/config/app.ts`: Fix and Helper share one per-user counter (`fix_take` in the database): 6 a minute and 10 per rolling 24 hours, sized for Groq's free plan.
- Charts on the web are drawn by Plotly.js, Vega-Embed and BokehJS, loaded from their CDNs (`src/lib/charts.ts`).
- The Android app mirrors the web's rules through shared JSON fixtures in `tests/fixtures/`; its CI fails if the two drift.

## AI tools and services used

**In the product**

- **Groq, `openai/gpt-oss-120b`** (called from the Vercel server, never from the browser): Fix and the Online helper.
- On Android only: **Qwen2.5-Coder-0.5B-Instruct** (Q4_0 GGUF) run on the phone with **llama.cpp**; see the Android README.
- The AI only proposes code. You accept a Fix diff or tap Insert; it never runs code, edits note text or sets an outcome.

## Status and limits

- The web app is live and in use by its author. It has not had outside users or a security audit.
- Fix and Helper use Groq's free tier: at most 10 requests per user per rolling 24 hours (6 per minute), and they stop when Groq's shared quota runs out.
- Run on server is Pro only, and only the author's account is Pro; there are no payments.
- Browser Python is limited to what Pyodide supports (no native packages outside Pyodide's set, no threads, no network sockets).
- The full Content Security Policy ships as Report-Only (`next.config.ts`).
- Confirmation email goes through a free SMTP relay without a custom domain, so it may land in spam.
